# 安全与加固

## 概览

面向 Web 应用的安全优先开发实践。将每个外部输入视为恶意输入，将每个密钥视为必须保护的机密，并将每项授权检查视为强制要求。安全不是一个阶段，而是所有处理用户数据、身份认证或外部系统的代码都必须遵守的约束。

## 使用时机

- 构建任何接受用户输入的功能
- 实现身份认证或授权
- 存储或传输敏感数据
- 集成外部 API 或服务
- 添加文件上传、Webhook 或回调
- 处理支付或 PII 数据

## 流程：先进行威胁建模

没有威胁模型就直接添加控制措施，得到的往往只是猜测。在加固前，花五分钟从攻击者角度思考：

1. **绘制信任边界。** 不可信数据在哪里进入系统？HTTP 请求、表单字段、文件上传、Webhook、第三方 API、消息队列和 **LLM 输出**都是边界；还包括那些因由操作系统交付而看似内部的本地值：另一个进程的命令行或环境变量、共享卷上的文件名、作业负载中的路径。信任取决于谁*写入*了值，而不是值通过哪个通道传递。每个边界都是攻击面。
2. **列出资产。** 哪些东西值得窃取或破坏？凭据、PII、支付数据、管理员操作和资金转移。
3. **对每个边界执行 STRIDE**：这是一种快速视角，不是形式主义：

| 威胁 | 要问的问题 | 典型缓解措施 |
|---|---|---|
| **S** 欺骗 | 是否有人可以冒充用户或服务？ | 身份认证、签名验证 |
| **T** 篡改 | 数据能否在传输中或静态存储时被修改？ | 完整性检查、参数化查询、HTTPS |
| **R** 否认 | 之后能否否认某项操作？ | 记录安全事件的审计日志 |
| **I** 信息泄露 | 数据能否泄漏？ | 加密、字段允许列表、通用错误 |
| **D** 拒绝服务 | 系统能否被压垮？ | 速率限制、输入大小上限、超时 |
| **E** 权限提升 | 用户能否获得不应拥有的权限？ | 授权检查、最小权限 |

4. **将滥用场景写在用例旁边。** 对每项功能询问“我会如何滥用它？”然后将其作为第一项测试。

如果无法说清一项功能的信任边界，就还没有准备好保护它。这属于 OWASP **A04：不安全设计**，大多数入侵始于设计，而不是代码。

## 三层边界体系

### 必须执行（无例外）

- 在系统边界（API 路由、表单处理器）验证所有外部输入
- 参数化所有数据库查询，绝不将用户输入拼接到 SQL 中
- 对输出进行编码以防止 XSS（使用框架自动转义，不要绕过它）
- 所有外部通信使用 HTTPS
- 使用 bcrypt/scrypt/argon2 对密码进行哈希（绝不存储明文）
- 设置安全响应头（CSP、HSTS、X-Frame-Options、X-Content-Type-Options）
- 会话使用 httpOnly、secure、sameSite Cookie
- 每次发布前使用检测到的包管理器，针对已提交的锁文件执行原生审计

### 先请求批准（需要人工批准）

- 添加新的身份认证流程或修改认证逻辑
- 存储新的敏感数据类别（PII、支付信息）
- 添加新的外部服务集成
- 修改 CORS 配置
- 添加文件上传处理器
- 修改速率限制或节流
- 授予提升的权限或角色

### 绝不执行

- 绝不将密钥提交到版本控制（API 密钥、密码、令牌）
- 绝不记录敏感数据（密码、令牌、完整信用卡号）
- 绝不将客户端验证作为安全边界
- 绝不为方便而禁用安全响应头
- 绝不对用户提供的数据使用 `eval()` 或 `innerHTML`
- 绝不将会话存储在客户端可访问的存储中（例如用于认证令牌的 localStorage）
- 绝不向用户暴露堆栈跟踪或内部错误细节

## 加固控制

下面的规则构成工作流；每条规则的具体实现位于 [references/hardening-patterns.zh-CN.md](references/hardening-patterns.zh-CN.md)。到达相关代码时再打开所需章节。

### 注入、XSS 与访问控制

- 参数化每个查询。绝不根据输入字符串构造 SQL、NoSQL 或 Shell 命令。
- 通过框架自动转义编码输出。如果无法避免原始 HTML，先使用允许列表清理器进行清理。
- 每个请求都检查**授权**，而不只是身份认证：已认证用户必须拥有或获准访问特定资源（A01、IDOR）。

模式：[注入](references/hardening-patterns.zh-CN.md#注入)、[XSS](references/hardening-patterns.zh-CN.md#跨站脚本xss)、[访问控制](references/hardening-patterns.zh-CN.md#访问控制失效)。

### 身份认证与会话

- 使用 bcrypt（≥12 轮）、scrypt 或 argon2 哈希密码。会话密钥来自环境变量，绝不写在代码中。
- 会话 Cookie 使用 `httpOnly`、`secure` 和 `sameSite: 'lax'` 或 `'strict'`（CSRF 防御；`'none'` 会在跨站请求中发送 Cookie），并设置有界的 `maxAge`。

模式：[身份认证](references/hardening-patterns.zh-CN.md#身份认证失效)。

### 响应头、CORS 与响应

- 每个响应都设置安全响应头（helmet 或框架等效机制）；CSP 从 `default-src 'self'` 开始并收紧，而不是放宽。
- CORS 限制为配置中的显式来源列表。带凭据时绝不使用 `*`。
- 在任何响应之前移除敏感字段（`passwordHash`、重置令牌）。错误正文应通用；内部信息仅写入服务器日志。

模式：[配置错误](references/hardening-patterns.zh-CN.md#安全配置错误)、[敏感数据暴露](references/hardening-patterns.zh-CN.md#敏感数据暴露)。

### 输入验证与上传

- 在边界使用模式验证：允许列表中的结构、长度、枚举值和格式。使用 422 和结构化详情拒绝；下游代码只使用已解析且已类型化的值。
- 上传：允许列表限制 MIME 类型，限制大小，并在重要场景验证内容（魔数）。扩展名不能证明任何事情。

模式：[模式验证](references/hardening-patterns.zh-CN.md#边界处的模式验证)、[文件上传](references/hardening-patterns.zh-CN.md#文件上传安全)。

### 服务端获取 URL（SSRF）

用户影响的任何 URL（Webhook、从 URL 导入、图片代理、链接预览）都可能被指向内部服务。允许列表限制协议和主机，解析**所有** DNS 记录并拒绝任何私有或保留地址（环回、链路本地 `169.254.169.254`、私有地址、IPv4 和 IPv6 的唯一本地地址），并禁止重定向。该检查仍存在 DNS 重绑定 TOCTOU 缺口：高风险场景应固定解析出的 IP，或在前面放置过滤代理。

模式：[SSRF](references/hardening-patterns.zh-CN.md#服务端请求伪造ssrf)。

### 对派生路径执行破坏性操作

删除、移动或覆盖的安全性取决于命名目标的值；信任取决于谁*写入*该值，而不是值通过哪个通道传递：另一个进程的命令行与表单字段一样受攻击者控制。形状检查只能证明格式正确，不能证明授权。调用前必须同时满足三点：解析后的目标（已解析符号链接）位于**允许列表根目录**下；目标至少比根目录深一层；并且具有**在操作前读取的所有权证据**。拒绝时记录被拒绝的目标并停止，绝不回退到更宽泛的默认路径。

检查为何比表面上弱（标记自证、检查/使用竞态）：[破坏性路径](references/hardening-patterns.zh-CN.md#派生路径上的破坏性操作)。示例代码：[安全检查清单](references/security-checklist.zh-CN.md#破坏性路径操作)。

### 速率限制

一般 API 应限制速率，认证端点应严格限制（约每 15 分钟 10 次尝试）。一旦有多个进程提供流量，内存计数器会静默变成 `max × instances`，在无服务器环境中甚至不会触发：使用共享存储支持限制器。

模式：[速率限制](references/hardening-patterns.zh-CN.md#速率限制)。

### 密钥

密钥来自环境变量。`.env.example` 提交时使用占位值；真实 `.env*` 文件和密钥材料应加入 gitignore；提交前检查暂存区差异。**密钥一旦到达远程仓库，就在落地的瞬间视为已泄露：先轮换，再清理历史。**

模式：[密钥管理](references/hardening-patterns.zh-CN.md#密钥管理)。

### 依赖与供应链

1. **找到安装边界和包管理器。** 使用拥有锁文件的工作区根目录；只有独立嵌套项目位于父工作区之外时才将其视为独立项目。核对 `packageManager`（如有）、锁文件和 CI；出现不一致或竞争性锁文件时停止。固定包管理器版本。
2. **在首次执行前阻止依赖脚本。** 使用禁用脚本或有文档记录的失败关闭策略进行引导，检查待执行脚本的源代码，仅批准最低限度的脚本，提交该策略，然后通过干净的冻结/不可变安装验证。绝不批量批准。
3. **每次发布前针对已提交锁文件运行原生审计。** 根据**可达性**（运行时、构建、测试、部署路径）和修复可用性处理 critical/high。绝不自动应用强制修复（`npm audit fix --force` 或等效命令），因为强制修复可能跨越声明的依赖范围；应预览、阅读变更日志，并逐项测试升级。每次延期都记录原因和复查日期。
4. **审计只能匹配已知公告。** 它不能发现新恶意或 typosquat 包（`cross-env` 与 `crossenv`）。同时审查新依赖、锁文件差异和脚本策略变更：所有权、维护情况、发布时长、来源和传递依赖图。在支持时验证注册表签名（`npm audit signatures`、`pnpm audit signatures`），将缺少签名视为需要调查的信号，而不是自动认定已被入侵（A06、LLM03）。

分类决策树：[依赖审计分类](references/hardening-patterns.zh-CN.md#依赖审计分类)。包管理器矩阵和安装脚本门禁：[安全检查清单](references/security-checklist.zh-CN.md#依赖安全)。

### 个人数据与隐私

加固关注“攻击者能否读取它？”隐私关注“我们是否应该持有它，以及持有多久？”最容易保护、泄露影响最小且合规成本最低的数据，是从未收集的数据；将个人数据视为需要最小化的责任。

- **添加字段时分类**（非个人、PII、敏感），并按类别处理。无法找到的数据，就无法保护或响应删除请求。
- **仅为明确目的收集。** “以后可能有用”是潜在泄露范围，不是目的。将 PII 排除在遥测之外。
- **预先设定保留期限并真正删除。** 每个个人数据存储都需要 TTL 和可用的删除路径，包括备份、缓存、搜索索引和分析副本。
- **支持管辖区要求的数据主体权利**（GDPR、CCPA 等）：导出、更正、删除。设计数据架构，使用户数据可查找且可擦除，而不是不可逆地散落在系统中。
- **收集和第三方共享都必须经过同意，并且可审计。** 将 PII 发送给分析、广告或 LLM 供应商属于共享；供应商需要数据处理协议。将区域设计为可配置策略，而不是硬编码假设。

分类表：[数据分类](references/hardening-patterns.zh-CN.md#数据分类)。隐私事件会启动数据泄露通知时钟；使用 `debugging-and-error-recovery` 技能进行复盘。

### AI / LLM 功能

调用 LLM（聊天机器人、摘要器、代理、RAG）会增加新的攻击面；将其映射到 [OWASP LLM 应用十大风险（2025）](https://genai.owasp.org/llm-top-10/)：

- **模型输出是不可信输入**（LLM05）。绝不将其传入 `eval`、SQL、Shell、`innerHTML` 或文件路径；先防御性解析，按模式验证，再编码。
- **提示词可能被劫持**（LLM01）。上下文中的不可信文本（用户消息、抓取页面、PDF）可能携带指令。系统提示词不是安全边界；通过代码强制执行权限。
- **将密钥、其他租户的数据和完整系统提示词排除在上下文窗口之外**（LLM02、LLM07）；限制工具权限，验证每个工具参数，并确认破坏性操作（LLM06）；限制令牌数、请求速率和递归深度（LLM10）；按租户隔离 RAG 嵌入，并在索引前验证文档（LLM08）。

模式：[LLM 输出处理](references/hardening-patterns.zh-CN.md#llm-输出处理)。

签字确认前，逐项检查[安全检查清单](references/security-checklist.zh-CN.md)：它涵盖身份认证、授权、输入、数据保护与隐私、响应头和 CORS、依赖与供应链、AI/LLM 以及错误处理，还包括 OWASP 快速参考表。

## 常见合理化说法

| 合理化说法 | 现实 |
|---|---|
| “这是内部工具，安全不重要” | 内部工具也会被入侵。攻击者会攻击最薄弱的环节。 |
| “以后再加安全措施” | 事后加固比一开始就加入难 10 倍。现在就加入。 |
| “没人会尝试利用这个” | 自动化扫描器会发现它。隐蔽性不等于安全。 |
| “框架会处理安全问题” | 框架提供工具，不提供保证。仍需正确使用。 |
| “这只是原型” | 原型会变成生产系统。从第一天养成安全习惯。 |
| “威胁建模过度了” | 花五分钟思考“我会如何攻击它？”，可以避免之后任何控制措施都无法修补的设计缺陷。 |
| “只是 LLM 输出，只是文本” | 这段“文本”可能是 SQL 语句、脚本标签或 Shell 命令。将其视为不可信输入。 |
| “审计通过了，所以依赖是安全的” | 审计匹配已知公告，不会检测新恶意包，也不会让未经审查的安装脚本变得安全。 |
| “先收集，以后可能需要” | 不持有的数据无法被泄露、传唤或错误删除。“可能需要”是泄露范围，不是目的。 |
| “手工处理删除请求” | 手工擦除会遗漏备份、缓存和分析副本。如果架构找不到用户数据，就无法履行请求，应为此设计。 |
| “合规是法务的问题，不是我们的问题” | 导出、删除、保留和同意都属于架构和代码。PII 散落在十个系统后，法务无法事后补救。 |

## 红旗

- 用户输入直接传入数据库查询、Shell 命令或 HTML 渲染
- 删除、移动或覆盖的目标来自负载、配置值或另一个进程的命令行，却仅通过路径形状检查保护
- 源代码或提交历史中存在密钥
- API 端点没有身份认证或授权检查
- 缺少 CORS 配置或使用通配符（`*`）来源
- 认证端点没有速率限制，或多个实例前使用内存限制器
- 向用户暴露堆栈跟踪或内部错误
- 存在已知 critical 漏洞、同一安装边界有竞争性锁文件、安装不可复现或脚本被批量批准的依赖
- 服务端获取用户提供的 URL 时没有允许列表（SSRF）
- LLM/模型输出被传入查询、DOM、Shell 或 `eval`
- LLM 上下文中放入密钥、PII 或完整系统提示词
- 收集个人数据却没有明确目的、保留期限或删除路径
- 未经同意或没有数据处理协议就将 PII 发送给分析、广告或 LLM 供应商
- “删除我的账户”只切换了标记，而个人数据仍留在存储和备份中

## 验证

实现安全相关代码后：

- [ ] 原生审计没有未缓解且可达的 critical/high 问题；CI 保留权威锁文件并阻止未经审查的依赖脚本
- [ ] 源代码和 Git 历史中没有密钥
- [ ] 所有用户输入都在系统边界验证
- [ ] 破坏性文件系统操作先解析符号链接，再验证允许列表根目录、最小深度和所有权，然后执行
- [ ] 每个受保护端点都检查身份认证和授权
- [ ] 响应中存在安全响应头（使用浏览器开发者工具检查）
- [ ] 错误响应不暴露内部细节
- [ ] 认证端点启用速率限制；多个实例提供服务时使用共享存储
- [ ] 服务端 URL 获取根据允许列表验证（无 SSRF）
- [ ] LLM/模型输出在使用前经过验证和编码（如存在 AI 功能）
- [ ] 个人数据已分类、按明确目的最小化，并设有保留期限
- [ ] 删除和导出请求端到端有效（包括备份、缓存和分析副本）
